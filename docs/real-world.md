# Real-world measurement report

[← Back to README](../README.md) · [简体中文](zh/real-world.md)

> All samples are real frontend repositories, anonymized as Repo A / Repo B / Repo C. Everything ran on copies; the original repositories were not modified, not committed to, and no files were generated in them. All numbers are real measured results.
>
> Version labels v3–v6.2 below refer to internal pre-release iterations; the first public release (0.1.0) includes all of them.

## Samples and execution

| Sample | Type | Size (src) | Stack | Why chosen |
| --- | --- | --- | --- | --- |
| **Repo A** | Older / messier | 402 source files, ~109k lines | Vue 3.2, axios 0.27, dayjs + moment-mini, npm, `.eslintrc.cjs` | A typical admin dashboard that has "run for years and passed through many hands": mixed JS/Vue, old and new dependencies coexisting |
| **Repo B** | Newer / more disciplined | 480 source files, ~180k lines | Vue 3.4, pnpm workspace, TS, per-app ESLint, vitest | A newer monorepo, to see how the tool behaves on a "more disciplined but more complex" repository |
| **Repo C** | Frontend + backend in one repo | frontend subdirectory | Vue 3.5 + TS 5.9 + vue-tsc 3.3 + ESLint 10 + pnpm | git root at the repo top level (contains backend / frontend), fe-guard root = frontend; verifies subdirectory-root support |

How it was run:

- The whole repository (including `node_modules` and `.git`) was copied to a local temporary copy with `rsync -a`; all `init` / `baseline` / `check` runs happened only in the copy.
- The original repositories were only inspected read-only (reading `package.json`, `git log`); no writes, no branch switches, no commits.
- Neither Repo A nor Repo B had dependency-cruiser installed, so the `boundaries` check was disabled (see the v6.1 section below for the boundaries measurement).
- Repo A used the default ESLint; Repo B is a monorepo whose root ESLint config conflicts with the sub-app configs, so in the early runs `eslint` was disabled and `tsc` was pointed at one app's `tsconfig.json`.

## False-positive judgments

Sampling: 3–20 items per check type were reviewed by hand; if fewer existed, all were reviewed. The criterion: "does the problem this warning points at actually need fixing in this repository's context?"

| --- | --- | --- | --- |

| Repo A ui warn | 8 / 152 | 8 acceptable | Same-named empty-state / chart components under different feature directories are business partitions and should not block; `warn` is the right level |
| Repo A metrics/duplication | 12 / 70 | 12 real duplicates | Two near-identical request modules at 85.9% duplication; several chart files 99%+ identical |

**Error-level false positives after fixes: 0 / 1092 (0%).** 170 warn-level entries are "real but acceptable" signals (152 + 18), so we do not recommend changing the ui default to error and blocking same-named components across business partitions.

## Real bugs found and fixed

| Symptom | Root cause | Fix |
| --- | --- | --- |
| Report paths showed `../../../private/tmp/...`; ESLint results could not be filtered by repo path | On macOS `/tmp` is a symlink to `/private/tmp` and the tool returns realpath | `toRepoPath` now realpaths both the root and the file; unit test added |
| 4454 `ui/duplicate-name` entries | All 66 `index.vue` files were named `Index` | `index.*` uses the parent directory name; entry files are excluded from same-name detection |
| deps treated virtual modules, the icon plugin, and generated `.d.ts` as phantom dependencies | Virtual modules / auto-generated declarations were treated as npm packages | Skip `virtual:`/`~icons`/`#`/`\0`; deps does not scan `.d.ts` |
| 548 phantom dependencies in the monorepo | Only the root `package.json` was read | Recursively discover sub-package manifests and merge dependencies by "nearest package.json + ancestor workspaces"; transitive dependencies resolvable in node_modules are not phantom |
| `diff-size` failed on its own after init | The baseline was treated as an ordinary new file | The baseline path was added to `diff-size.ignore` |
| The `**/locales/**` ignore rule had no effect | Ignore matching did not support a leading `**/` | Added leading `**/` semantics plus a unit test |
| Component duplication detection treated `views/x/components/` as shared components | It only checked whether the path contained `components/` | Only `src/components/` or a repo-root `components/` counts as shared; everything else is downgraded to warn |

## v6.1: boundaries measured on a real repository

This closes the biggest unknown left from the early runs: `boundaries` measured on a real repository for the first time. The sample is Repo A (Vue 3.2, 402 source files / ~109k lines), copied to a local temporary copy; the original repo was read-only. dependency-cruiser **18.8.0** was installed in an isolated directory (so it does not pollute the sample's dependencies), and `checks.boundaries.bin` points at that directory's depcruise.

Rule config (`.dependency-cruiser.cjs`): `no-circular` plus two layer rules (`apis` / `utils` must not depend on `views`); `tsConfig: { fileName: 'tsconfig.json' }` resolves the `@/` alias, and `enhancedResolveOptions.extensions` includes `.vue`.

| Metric | Result |
| --- | ---: |
| Dependency-graph modules | 447 (including node_modules entries) |
| no-circular violations | 19, involving 16 files |
| Layer-rule violations | 0 |
| fe-guard check time | ~0.6–0.7s |
| check after baseline recording | exit code 0 |

False-positive sampling (3 cycles, import chains traced by hand):

1. A three-module cycle (api layer → utils layer → store module → api layer): a real three-node cycle.
2. A large cycle through the app entry (router guards → store → api → utils → entry → router guards): a real large cycle.
3. A real component cycle (three `.vue` components importing each other): a real component cycle.

**3/3 real issues, 0 false positives.** The adapter normalizes correctly: `boundaries/no-circular`, relative posix paths, `line: null`, severity passed through.

### Two pitfalls found in the measurement (both handled)

1. **depcruise 18 schema change**: `options.tsConfigFile` from older docs is now `options.tsConfig: { fileName }`. With an invalid config depcruise exits 1 and stdout is not JSON; fe-guard correctly reports "output is not valid JSON" and attaches stderr — no false pass, but adopters need to know the new syntax.
2. **Silent false pass in Vue parsing (adapter fixed)**: depcruise only parses `.vue` if it can import `@vue/compiler-sfc` (Vue 2 uses `vue-template-compiler`) **from its own install location**. When missing, it does not error — it simply excludes 224 of the 225 `.vue` files from the dependency graph (only 61 modules remain), and violations are always 0. Normal adoption (`npm i -D dependency-cruiser` inside the project) is unaffected because Vue projects ship compiler-sfc; but isolated installs / trimmed dependencies hit this. **Since v6.1 the adapter compares "`.vue` count on disk vs `.vue` count in the dependency graph" and, if incomplete, emits a non-baselineable `boundaries/not-executed`** (measured: remove compiler-sfc → reports `only parsed 1/225 .vue files` and exits 1; restore → normal). Regression test: `test/v61.test.js`.

Conclusion: `boundaries` is usable on a 100k-line Vue repo, fast (<1s), with no false positives in sampling; the biggest unknown — "boundaries never measured" — is closed. Still not covered: React/TSX repos, monorepo multi-package boundaries, and schema differences in older dependency-cruiser versions (≤16).

## v6.2: subdirectory-root re-verification (Repo C)

The sample switches to Repo C, a real target adoption repository: git root at the repo top level (contains backend / frontend), fe-guard root = `frontend` (Vue 3.5 + TS 5.9 + vue-tsc 3.3 + ESLint 10 + pnpm). Copied to a local temporary copy (excluding node_modules/dist); the original repo was read-only. The config enables only deps / metrics / diff-size.

Before v6.2, this layout had two confirmed defects: the `--staged` shadow directory was laid out from the git root (the shadow contained `frontend/src`), so checks scanned `src`, found nothing → false pass; and `diff-size` counted changes across the whole repo (including backend). Re-verified after the v6.2 fixes:

| Scenario | Result |
| --- | --- |
| Baseline recording | 13 metric-type legacy entries; check exits 0 |
| Stage a 700-line file, restore the working tree to clean | `check --staged` catches `metrics/file-lines`, exit code 1 (paths relative to frontend; before the fix it scanned empty and false-passed) |
| Append 1000 lines in backend | `check --full` exits 0; diff-size does not count sibling directories |
| Append 700 lines in frontend | `check --full` triggers `diff-size/lines`, exit code 1 |

Companion fixes (same git-path semantics): rename detection and `changedFiles` gained `--relative` + path scoping; `--verify` / rename migration now read the HEAD ledger via `HEAD:./<path>` (cwd-relative form). `test/v62.test.js` covers all the scenarios above with 5 end-to-end tests; the v5 root-directory snapshot regressions are unchanged.

Conclusion: in a frontend+backend single-repo layout, fe-guard with `--root frontend` is fully functional; hooks can use `--staged`, and diff-size can be enabled. When adopting, put the hook at the git root's `.git/hooks/pre-commit` and cd into frontend before running.

## Recommended adoption configuration

### Repository size and thresholds

| Size | maxFileLines | maxFunctionLines | maxAny | duplication.maxRatio | diff maxFiles / maxLines |
| --- | ---: | ---: | ---: | ---: | --- |
| New project / < 30k lines | 400 | 80 | 10 | 0.35 | 15 / 400 |
| Mid-size legacy / 30k–100k lines | 500 (default) | 100 (default) | 20 (default) | 0.5 (default) | 20 / 600 (default) |
| Large legacy / > 100k lines | 800 | 150 | 50 | 0.6 | 40 / 1200 |

Thresholds only affect **new** issues: legacy violations are already in the baseline. Raising thresholds does not let new code off the hook; it only reduces noise at first adoption.

### Which checks should start at warn

- `ui`: if the repo has multiple apps / business partitions, set `ui.level` to `warn` first and run for a week to judge warning quality; rebuilds of components from the shared component directory still appear in the report with error `severity`, they just don't block.
- `metrics`: if legacy files commonly exceed 1000 lines, raise thresholds per the table above first, then set `metrics.level` to `warn`; switch back to `error` once new-code habits stabilize.
- `deps`: `error` can be on by default, but `capabilities` must first be configured to match the repo's real wrappers; without configuration it only blocks phantom dependencies and new dependencies, with very few false positives.
- `eslint` / `typescript`: keep `error`; run `eslint --fix` once before adopting — Repo A's 361 `prefer-const` entries disappear directly.

### Adoption cost

- Copy / init: `npx fe-guard init` + `npx fe-guard baseline`, ~2 minutes.
- Config tuning: the defaults work as-is; monorepos are detected automatically and run per package.
- Files touched: `fe-guard.config.json`, `fe-guard.baseline.json`, and one spot each in CI/Husky.
- First-run warnings: 956 in Repo A, 136 in Repo B; after recording, `check` is all green.

## Rolling out across teams: where you get stuck first

1. **How ESLint is invoked in a monorepo** (the first blocker). The early `eslint` adapter could only run one command in one cwd; in a repo like Repo B where each app has its own config, the root config produced 431 parse-errors. Since v4, execution is grouped per package and run in parallel.
2. **Type checking Vue SFCs**. Plain `tsc` does not check `.vue`; since v4, detecting `.vue` automatically switches to `vue-tsc`, and it fails explicitly when not installed.
3. **The adoption cost of boundaries**. Neither sample had dependency-cruiser installed initially, and rules must be written from scratch; this is the check most likely to be skipped during rollout.
4. **Reviewing the baseline**. Recording legacy violations is a one-time action, but the baseline file gets large (~1300 lines in Repo A); agree that "baseline changes must be committed separately, with the reason spelled out".
5. **The psychological shock of first-run warnings**. Even with everything green after recording, seeing 956 warnings for the first time makes people want to switch the whole thing off; start with only `deps` + `metrics`, then enable `ui` gradually.

### Issues resolved in later versions

| Blocker at the time | Status now |
| --- | --- |
| How ESLint is invoked in a monorepo | Since v4, workspaces are detected automatically; ESLint / TypeScript run per package with their own configs in parallel; Repo B's 431 parse-errors dropped to zero |
| Type checking Vue SFCs | Since v4, detecting `.vue` switches to `vue-tsc` automatically; when missing it explicitly reports `typescript/vue-tsc-missing` instead of a fake 0 |
| Reviewing the baseline | Since v4, `baseline --show` groups by file with first-recorded dates; since v6, `--by-rule` sorts by cleanable count; `--verify` uses merge-base to block unregistered widening |
| The psychological shock of first-run warnings | Since v4, only new violations are listed individually by default; legacy collapses into a one-line summary, expanded only with `--all` |
| Hooks too slow to dare enable the full profile | Since v6, the `fast` profile runs only ESLint / deps / ui / metrics (measured 2.0s); the full profile is left for manual runs before merge; `doctor` shows coverage and timing first |

What still holds: without CI there is only the local default path, and `--no-verify` can still bypass it.

## React / TSX verification (0.4.x)

Two open-source React repositories were cloned and checked end-to-end with real tooling (no mocks):

| Repo | Shape | Checks that ran | Notes |
| --- | --- | --- | --- |
| alan2207/bulletproof-react (`apps/react-vite`) | React 18 + Vite + TS; the app is a git subdirectory; Storybook stories | eslint, tsc, ui, metrics, boundaries (an injected dependency-cruiser config plus a deliberate cycle fixture) | eslint / tsc clean before the fixtures; boundaries caught the cycle; the 56 phantom `ui/duplicate-name` errors disappeared |
| pmndrs/jotai | pnpm workspace (`packages: [".", "website"]`); React library with TSX tests; root flat config ignores `website/` | eslint, tsc, ui, metrics; `website` reported as skipped | root package ran once; one real `metrics/file-lines` finding remained |

Findings fixed during this verification:

1. **Storybook stories / tests were treated as components.** Repeated `Default` exports produced 56 duplicate-name errors. `*.stories.*`, `*.story.*`, `*.test.*`, `*.spec.*` and `__tests__` / `__mocks__` / `e2e` directories are now excluded from the component inventory.
2. **Subdirectory projects compared the wrong `package.json`.** New-dependency detection read the git-root manifest, so all 30 app dependencies looked unregistered. `git show base:./<path>` now resolves relative to the analysed project root.
3. **A package fully excluded by ESLint aborted the gate.** ESLint exits 2 when every file is ignored; that package is now recorded as `skipped` (visible in timings) instead of failing the whole check. Restoring a real lint range still catches violations.
4. **`pnpm-workspace.yaml` listing `"."` ran the root package twice.** The root is now deduplicated and executed once.

Scope: this verifies that the four checks run correctly on React / TSX; it does not claim reuse decisions (`ui`) are semantically right, and `boundaries` still needs a dependency-cruiser config.

## Boundaries of these conclusions

- The Vue findings come from 3 admin-style repositories; React / TSX was later verified on 2 open-source repos (Bulletproof React, Jotai). Mini-programs, SSR and component libraries are still uncovered.
- False-positive judgments are manual sampling, not full annotation; "real duplicates" in `metrics` only means "genuinely highly similar", not "should be merged for business reasons".
- Performance numbers come from single runs on this machine; no multi-round statistics, and no coverage of CI cold starts, cache hits, etc.
- The original repositories were not modified; in a real adoption, `init` generates `AGENTS.md`, `fe-guard.config.json`, `fe-guard.baseline.json`, `.fe-guard/`, etc. at the repo root — review them as a team before committing.

## On wiring `ui_lookup` into `task_plan`

Based on this data, **we do not recommend doing it now**:

- Component-inventory extraction has now been verified on React / TSX (stories and tests excluded, no phantom duplicates), but that only proves the structural signal works; it still doesn't prove a "should reuse" decision.
- `task_plan` is a high-frequency tool; stuffing component summaries into it adds 200–600 bytes to every plan call, and most plans have nothing to do with components.
- ui false positives in real repos are still mostly warn-level (170 entries), which shows "same name / high overlap" is only a clue — not enough for the workflow layer to make reuse decisions on a human's behalf automatically.

A better next step: run `ui` at warn for two weeks in 1–2 real repos, measure "when an AI-written component hits a warn, does the human actually choose to reuse", then decide whether to embed the lookup into `task_plan`.
